# Key Lifecycle Specification

Phase 31, item 5 of [docs/spec.md](../spec.md). Every key type this
protocol generates: how it's created, how long it lives, what rotates or
expires it, and — the part that matters most for an audit — exactly how
and when it's destroyed. Where the implementation falls short of what
`docs/spec.md` itself calls for, that's stated plainly rather than
smoothed over.

## Summary table

| Key | Type | Generated by | Lifetime | Destroyed by |
|---|---|---|---|---|
| Identity keypair | Ed25519 | `generateIdentity` | Long-term (no rotation mechanism — see below) | Not handled by this library (see "Gaps") |
| Signed prekey | X25519 | `generateSignedPreKey` | Medium-term, app-decided rotation, has `expiresAt` | Not handled by this library — rotation/deletion is the app's job |
| PQ prekey | ML-KEM-1024 | `generatePQPreKey` | Medium-term, app-decided rotation, has `expiresAt` | Same as above |
| One-time prekey | X25519 | `generateOneTimePreKeys` | Single use | `PrekeyStore.consumeOneTimePreKey` — private key `secureErase`d, entry marked `CONSUMED` |
| PQXDH ephemeral key (`EK_A`) | X25519 | `pqxdhInitiate` (fresh per attempt) | One session-establishment attempt | Erased immediately after `SK` is derived, inside `pqxdhInitiate` itself — never persisted at all |
| Ratchet DH keypair (`DHs`) | X25519 | `ratchetInitAlice`/`ratchetInitBob`, then fresh per DH ratchet step | Until the next DH ratchet step | Old `DHs.privateKey` erased on commit when superseded (`dhRatchetStep`) |
| Root key | 32 bytes | `KDF_RK` per DH ratchet step | Until the next DH ratchet step | Erased on commit when superseded |
| Chain key (send/receive) | 32 bytes | `KDF_RK` (fresh chain) / `KDF_CK` (advance) | Until the next message on that chain | Old chain key erased once the next one is derived |
| Message key | 32 bytes | `KDF_CK` per message | One AEAD operation | Erased immediately after use, **except** when skipped (see below) |
| Skipped message key | 32 bytes | `KDF_CK`, stored instead of used immediately | Until consumed, evicted, or the session is reset | See "Skipped key lifecycle" below — this is where the implementation has a real gap against `docs/spec.md`'s own stated policy |
| Session master key (at-rest encryption) | 32 bytes | App-supplied via `MasterKeyProvider` | App-decided | Not generated or destroyed by this library at all — see the integration guide's persistence section |

## Identity keys

Generated once (`generateIdentity`), long-term, `identityId` derived as
`Hash(canonicalIdentityPublicKey)` (`computeIdentityId`,
`src/identity/identity.ts`). The private key must never leave the device
(`src/identity/types.ts`'s own doc comment) and this library never
transmits it — `PublicIdentity` (the only identity projection that
crosses any boundary) has no field that could hold one.

**Rotation**: there is no identity-key rotation mechanism in this
protocol at all — an identity is generated once and used for the
device's lifetime. This is consistent with how Signal's own protocol
treats identity keys (rotating one is equivalent to re-provisioning the
device from a fingerprint-verification point of view), but is worth an
auditor confirming is an intentional design stance rather than an
oversight: it is — see `docs/spec.md`'s Phase 2, which defines identity
generation and fingerprinting but never a rotation flow.

## Signed prekeys and PQ prekeys

Generated with an explicit `expiresAt` (`generateSignedPreKey`/
`generatePQPreKey`, both take a validity duration), checked via
`isSignedPreKeyExpired`/`isPQPreKeyExpired`
(`src/prekeys/signedPrekey.ts`/`pqPrekey.ts`, re-exported from
`src/index.ts`). Unlike one-time prekeys, these are **reused across every
session established before their next rotation** — this is normal,
expected usage, not a bug (see the README's note on the second
`ratchetInitBob` aliasing fix, which was specifically caused by this
reuse pattern exposing a defensive-copy bug that single-session testing
never exercised).

**What this library does**: generation, expiry-checking, and signature
verification. **What it deliberately does not do**: decide a rotation
cadence, republish a rotated bundle anywhere, or delete an expired
prekey's private key. All of that is explicitly the integrating
application's responsibility (see `docs/integration-guide.md`'s "what
this library does not do" list, item 3) — this is a real gap in the
*application* an auditor would need to review, not a gap in this
library's own scope, and one worth flagging precisely for that reason:
an unrotated signed prekey has no automatic expiry enforcement anywhere
in this codebase beyond the boolean check a caller has to remember to
make.

## One-time prekeys

The one key type with a fully automated lifecycle in this codebase.
`PrekeyStore`'s `AVAILABLE → RESERVED → CONSUMED` state machine
(`src/prekeys/PrekeyStore.ts`, `InMemoryPrekeyStore.ts`):

- **`AVAILABLE`**: generated (`generateOneTimePreKeys`, batch-generated —
  generate dozens up front, not one at a time), not yet used by anyone.
- **`RESERVED`**: a `SESSION_INIT` referencing this id is being processed
  (`PQXDHResponder.ts`) — reserved *before* attempting decryption, so a
  concurrent second use of the same id during processing is impossible
  (Phase 3's atomicity requirement — currently process-local, relying on
  JS's synchronous execution model; see the cryptographic design
  document's note on what a persistent backend implementing this
  interface must guarantee).
- **`CONSUMED`**: committed only *after* the initial message actually
  decrypts successfully (`SessionManager.processNewSessionInit`) — on
  failure, the reservation is released back to `AVAILABLE`, never left
  stuck (`test/session/SessionManager.test.ts`'s Phase 5.3 tests). The
  private key is `secureErase`d at the moment of consumption
  (`test/prekeys/prekeyStore.test.ts`: "consume transitions RESERVED ->
  CONSUMED and erases the stored private key").
- A consumed id can never transition back to `AVAILABLE`
  (Invariant 5 — `docs/security-invariants.md`).

One-time prekeys are the **only** prekey type not signed in the wire
format — see the cryptographic design document's domain-separation table
and `docs/audit/dependency-inventory.md`'s fuzzing cross-reference for
why that's a verified-safe design property, not an oversight.

## Ephemeral and ratchet keys

Covered in full detail by the cryptographic design document's key
hierarchy and `docs/security-invariants.md` (Invariants 1, 4, 6). Summary
for this document's purposes: every ratchet-layer key (`DHs`, root key,
both chain keys, message keys) is erased via `CryptoProvider.secureErase`
the moment it's superseded or consumed, structurally — the
clone-then-commit pattern (`src/ratchet/DoubleRatchet.ts`) means a
*failed* decrypt attempt never mutates or destroys anything, only a
*successful* one commits, and only the commit path erases the values it
superseded.

## Skipped key lifecycle — a real gap against the spec's own stated policy

`docs/spec.md` (line 921) states skipped keys should be "delete[d]
after: successful use, expiry, session reset, or **security-policy
timeout**." This codebase implements exactly two of those four triggers
directly, plus two size-based bounds the spec doesn't literally
enumerate there but that serve the same purpose:

| Trigger | Implemented? |
|---|---|
| Successful use | **Yes** — `ratchetDecrypt` deletes the matched entry from `skippedMessageKeys` on successful decrypt (`src/ratchet/DoubleRatchet.ts:277`) |
| Session reset | **Yes** — `SessionManager.resetSession`/`receiveSessionReset` erase and clear the entire `skippedMessageKeys` map (`destroySessionState`, Phase 19) |
| Per-call bound (`MAX_SKIP` = 1000) | **Yes**, though not literally named in the spec's own table — bounds how many keys a single out-of-order message can force derived |
| Global cumulative bound (`MAX_STORED_SKIPPED_KEYS` = 2000) | **Yes** — see `docs/security-invariants.md`'s Invariant 3 entry, including the regression test this project's own security-invariants review found was missing and added |
| **Time-based expiry** | **No.** There is no timestamp on a skipped-key entry (`skippedKeyIndex` is keyed only by `(ratchetPublicKey, messageNumber)`, with no stored creation time), and nothing in `DoubleRatchet.ts`, `SessionManager.ts`, or the persistence layer ever evicts an entry purely because time has passed. |
| **Security-policy timeout** | **No** — same gap; there is no separate "timeout" mechanism distinct from the size caps above. |

**Practical consequence**: a skipped key that's never matched by a
later out-of-order delivery, and never evicted by the size caps because
the store stays under 2000 entries, sits in memory (and in a persisted
session record — `SerializedSession.skippedMessageKeys` round-trips it
unchanged) indefinitely, until either the message finally arrives, the
session is reset, or the cap is hit by *other* skipped keys. This is
bounded (the global cap guarantees it can't grow unboundedly — Invariant
3 still holds), but it is not the "expiry" behavior `docs/spec.md`
explicitly calls for. This is a legitimate, real finding for the actual
security audit to weigh — most likely low severity given the size bound
already exists, but worth a deliberate decision (implement a real TTL,
or explicitly accept the size-bound-only behavior as sufficient) rather
than leaving it as an unnoticed gap between the spec and the code.

## Session master key (persistence)

Entirely out of this library's scope by design — see
`docs/integration-guide.md`'s persistence section and
`src/persistence/types.ts`'s `MasterKeyProvider` doc comment.
`StaticMasterKeyProvider` (a fixed, caller-supplied key) is explicitly
test-only. This document doesn't repeat that guidance; it's flagged here
only so the key-lifecycle picture is complete: this is the one key type
in the entire system whose generation, rotation, and destruction policy
is 100% the integrating application's responsibility, not something an
audit of *this* codebase can evaluate in isolation.
